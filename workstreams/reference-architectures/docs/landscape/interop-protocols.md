# Interop Protocols

MCP and A2A — protocols for the tool-integration surface between a model-hosting application and its tools, and for peer-to-peer agent delegation across a boundary where no shared orchestrator exists, respectively. Part of the [landscape survey](README.md); see [`../references.md`](../references.md) for sourcing.

## MCP

The Model Context Protocol (see [Model Context Protocol specification (2025-06-18)](https://modelcontextprotocol.io/specification/2025-06-18)) is a JSON-RPC 2.0-based protocol, at specification revision `2025-06-18`, for stateful connections between a **Host** (the LLM application initiating connections), a **Client** (a connector within the host), and a **Server** (a service providing context and capabilities), with capability negotiation and BCP 14 / RFC 2119 keywords used normatively throughout the spec itself. Servers expose three feature categories — Resources, Prompts, and Tools — and clients may offer Sampling, Roots, and Elicitation back to servers; utilities cover configuration, progress tracking, cancellation, error reporting, and logging.

MCP is usefully understood by analogy to the Language Server Protocol: LSP standardized the integration surface between an editor and a language's tooling without standardizing editors themselves, and MCP does the analogous thing for the integration surface between a model-hosting application and tools, without standardizing models or tools themselves. That analogy also explains MCP's deliberate modesty about what it enforces: the specification states plainly that tools "represent arbitrary code execution and must be treated with appropriate caution," that "descriptions of tool behavior such as annotations should be considered untrusted, unless obtained from a trusted server," and that hosts must obtain explicit user consent before invoking any tool — and, most consequentially for this RA, that MCP "itself cannot enforce these security principles at the protocol level." Both RA files quote this line directly, because it is the textual basis for the RA's position — argued in `P4 AgentStep`'s own justification, now in [`ra/primitives/`](../../ra/primitives/README.md) — that the workflow rather than the tool server must be authoritative on a tool's effect classification.

## A2A

A2A (see [A2A Protocol specification](https://a2a-protocol.org/latest/)) is a Linux Foundation project (see [Linux Foundation — Agent2Agent Protocol project](https://www.linuxfoundation.org/press/linux-foundation-launches-the-agent2agent-protocol-project-to-enable-secure-intelligent-communication-between-ai-agents)), under the same foundation umbrella AAIF itself was formed within (see [Linux Foundation — Agentic AI Foundation formation](https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation)). Its role in this landscape is peer-to-peer agent delegation across a boundary where no shared orchestrator exists — exactly `ra-multi-agent.md`'s reason 3 for crossing from a single `AgentStep` into a multi-agent topology ("organisational or trust boundaries"), and exactly topology T4's binding.
