# Process Standards

BPMN 2.0, DMN, and CMMN — mature, pre-agentic OMG standards for process flow, decision logic, and knowledge-work case management. Part of the [landscape survey](README.md); see [`../references.md`](../references.md) for sourcing.

## BPMN 2.0

BPMN 2.0 (see [OMG BPMN 2.0](https://www.omg.org/spec/BPMN/2.0/)) is a mature OMG standard for modeling deterministic business processes as a directed graph of flow nodes connected by sequence flows, executed under token semantics: a token enters at a start event, moves along sequence flows, and is consumed or split at gateways and joined at parallel gateways, with the process instance completing when all tokens reach an end event. Its task vocabulary distinguishes *what kind* of work a step performs — service tasks (system-invoked), user tasks (human-performed), business rule tasks (typically bound to a DMN decision), send/receive tasks (message-oriented) — which gives a reviewer a typed vocabulary for what a step *is* before looking at its implementation. Gateways (exclusive, inclusive, parallel, event-based) externalize branching logic into the diagram rather than into code. Boundary events attached to an activity — error, timer, message, escalation, compensation — give a declarative way to say "if this specific thing happens to this specific activity, go here instead," and event sub-processes generalize the same idea to a whole process scope. Multi-instance activities run a single activity definition over a collection, with a `completionCondition` that can stop the collection early. Call activities invoke a separately defined process as a reusable unit; message flow between separate pools models communication across two independently-run processes — for example, two different organisations' BPMN processes — which, together with a call activity, is BPMN's nearest equivalent to a cross-boundary `P16 Handoff`. Compensation handlers define a semantic undo for an activity that already completed, invoked when a compensation event fires.

**What BPMN 2.0 gives an implementer for free:** a reviewable graphical (or XML-serializable) representation of control flow, a mature and widely implemented boundary-event vocabulary for typed failure and timeout handling, a native saga-like compensation mechanism, and — critically for this RA — the `extensionElements` mechanism, which lets an implementer attach vendor- or domain-specific semantics to any BPMN element without forking the notation or waiting on an OMG revision. Camunda's `zeebe:adHoc` configuration inside `extensionElements` (see [Camunda — Ad-hoc sub-processes](https://docs.camunda.io/docs/components/modeler/bpmn/ad-hoc-subprocesses/)) is the concrete precedent: it adds agent-relevant configuration to a standard `bpmn:adHocSubProcess` element without altering the BPMN schema itself. This matters more than it might first appear, because `extensionElements` is very plausibly this RA's most likely binding path into an existing, deployed BPMN engine — it lets the `AgentStep` boundary contract's eight elements be expressed as engine-specific extension data riding on a standard element, rather than requiring every BPMN-based vendor to adopt a new element type before any of this is implementable.

**What BPMN 2.0 does not give an implementer, and cannot without an extension:** no native resource-consumption ceiling (`completionCondition` bounds a multi-instance collection, not tokens, cost, or wall-clock spend); no machine-readable confidence or uncertainty signal on a task's output; and, as `ra-single-agent.md` documents from the Camunda ad-hoc sub-process's internally-handled implementation, no mechanism for a running instance's element set to be reconfigured mid-execution rather than only on entry. Camunda's own AI Agent Sub-process connector documents a configurable limit on the number of model calls the agent may make — the closest built-in resource-consumption guard found anywhere in this landscape, and still only a partial one: it caps call count, not token spend or dollar cost (see [`../gap-analysis.md`](../gap-analysis.md)).

## DMN

The Decision Model and Notation standard (see [OMG DMN](https://www.omg.org/spec/DMN/)) separates decision logic from process flow: a Decision Requirements Diagram (DRD) shows which decisions depend on which other decisions and which input data, and each decision node's logic is typically expressed as a decision table — a set of rules, each mapping input conditions to an output, disambiguated by a declared hit policy (for example, first-match, unique-match, or collect-all-matches) when more than one rule could otherwise fire. FEEL (Friendly Enough Expression Language) is DMN's expression language for conditions and outputs, designed to be readable by a business analyst rather than only a developer.

**What DMN gives for free:** a reviewable, testable, versionable representation of exactly the class of logic this RA's determinism-hints table recommends for "closed-set classification with stable labels" and "arithmetic, eligibility, thresholds, entitlement" — the cases where "an LLM is an unreliable calculator for a solved problem" (`ra-single-agent.md`, determinism hints). **What it does not give:** any mechanism for the genuinely open-ended case — a decision table has no answer for an input space that cannot be enumerated into rows.

## CMMN

The Case Management Model and Notation standard (see [OMG CMMN](https://www.omg.org/spec/CMMN/)) models knowledge work whose path is not fully predictable at design time. A case operates over a **case file** — the evolving data the case works with — through a **case plan model** composed of **stages**, which can contain **discretionary items**: tasks and sub-stages that are available to be planned into the case at the discretion of a case worker, rather than fixed into the plan in advance. **Sentries** are the entry/exit criteria that trigger a stage or milestone transition, and **milestones** mark achieved states within the case.

CMMN's discretionary-item model is the closest conceptual match, in any pre-agentic standard, to "the agent chooses what to do next." A discretionary item is, structurally, a menu of things a competent actor *may* choose to do given the current state of the case file — which is a reasonable description of what an `AgentStep`'s tool scope is: a bounded menu of `P5 ToolCall` candidates the agent may select from, given the current state of its input contract. CMMN never had to solve the specific problems this RA solves — there is no CMMN notion of a token budget on how many discretionary items a case worker may plan in, no confidence signal on a case worker's choice, and no compensation handler tied to a discretionary item the way BPMN ties one to an activity — but the shape of "bounded, declared menu of eligible next actions, chosen by an actor rather than fixed by a graph" is exactly the shape `ra-multi-agent.md` reaches for when it names CMMN's case file as "the nearest standards concept" for `P17 SharedContext` in topology T5. This is an underexplored point worth the WG's attention: CMMN predates the agentic era by over a decade and was solving a human-case-worker version of the same structural problem this RA solves for an agent.
