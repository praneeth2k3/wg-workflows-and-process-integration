# Agent Frameworks

LangGraph, CrewAI, Microsoft AutoGen / Agent Framework, and the OpenAI Agents SDK: where multi-agent coordination constructs already exist as product features, each with its own vocabulary. Part of the [landscape survey](README.md); see [`../references.md`](../references.md) for sourcing.

## LangGraph

LangGraph (see [LangGraph documentation](https://langchain-ai.github.io/langgraph/)) models an agent or multi-agent system as a `StateGraph`: a set of nodes connected by edges, where edges can be conditional (the next node is chosen by evaluating the current state) rather than fixed. State moves through the graph via named channels, and channels can be reducer-based: a channel's update function combines a node's output with the channel's existing value, rather than simply overwriting it, which is the mechanism `ra-multi-agent.md` names as the nearest framework-level equivalent to `P17 SharedContext`'s consistency-model requirement. Checkpointers persist graph state keyed to a thread, which is LangGraph's durable-resume mechanism (`P12 StateCommit`'s equivalent) and also what makes `interrupt()` possible: a node can pause graph execution and wait for external input to resume from exactly that point, which is LangGraph's human-pause primitive (`P6 HumanCheckpoint`'s equivalent). Subgraphs let a whole graph be nested inside a node of another graph (a natural fit for `P4 AgentStep` as a bounded container, and for supervisor/worker composition in topology T1), and `create_react_agent` is LangGraph's prebuilt helper for constructing exactly that kind of bounded reasoning-and-tool-use subgraph. This is LangGraph's nearest equivalent to `P4 AgentStep` itself. A dedicated tool node executes a tool call and returns its result to the graph, which is `P5 ToolCall`'s nearest equivalent. `Send` supports dynamic fan-out, spawning a variable number of parallel node invocations decided at run time rather than fixed in the graph definition (`P7 FanOut/FanIn`'s mechanism for the dynamic case), and `Command` supports handing control directly to a named node, including one in a different subgraph, which is `ra-multi-agent.md`'s cited nearest equivalent to `P16 Handoff` (`Command(goto=...)`).

**What LangGraph gives for free:** essentially the richest node/edge/state vocabulary of any framework surveyed, a durable-pause primitive, and dynamic fan-out. **What it does not give:** no budget ceiling (an unbounded LangGraph loop is exactly the "no budget" anti-pattern), no compensation mechanism (`ra-single-agent.md`'s table marks this "a real gap" for LangGraph specifically), and (this survey's own observation, building on `ra-multi-agent.md`'s note that `Command` is `P16`'s nearest equivalent) no structural distinction between a `Command` handoff that transfers responsibility and a tool node that merely returns a result: both are graph-level constructs the developer has to choose to use correctly, with nothing in LangGraph itself enforcing that a handoff's authority, budget, and audit-continuity obligations (the seven elements `ra-multi-agent.md`'s handoff contract requires) are actually declared.

## CrewAI

CrewAI (see [CrewAI documentation](https://docs.crewai.com/)) organizes work around a `Crew` of `Agent`s executing `Task`s, under either a sequential process (tasks run in a fixed order) or a hierarchical process (a manager agent decomposes and delegates), and its `Flow` construct layers deterministic, event-driven control flow around and between agent-driven crews.

> **[verify]** This document does not have specific, session-confirmed detail on CrewAI's current memory model, delegation semantics, or exact API surface, and does not assert those specifics as fact.

The architecturally relevant point: CrewAI's hierarchical process (a manager agent delegating to worker agents) is a close product-level match to this RA's topology T1 (supervisor/orchestrator-worker), and its `Flow` construct is CrewAI's own acknowledgment that pure agent-to-agent delegation needs a deterministic wrapper around it, independently arriving at roughly the same "the workflow, not the agents, should own the coordination" position this RA argues from first principles.

## Microsoft AutoGen / Agent Framework

Microsoft AutoGen (see [Microsoft AutoGen](https://microsoft.github.io/autogen/)) supports group-chat-style multi-agent topologies, where a set of agents converses in a shared thread and a selection mechanism decides which agent speaks next, running on an actor-based runtime, with termination conditions determining when the group chat concludes.

> **[verify]** This document does not have specific, session-confirmed detail on AutoGen's current termination-condition vocabulary, its actor-runtime specifics, or how "Agent Framework" branding relates to AutoGen's positioning today, and does not assert those specifics as fact.

The architecturally relevant point: a group-chat topology with a speaker-selection mechanism is a form of multi-agent coordination this RA's topology catalog does not name directly. It is closer to `P17 SharedContext` (a shared conversational thread multiple agents read and write) than to any single `T1`–`T6` topology, and AutoGen's termination-condition concept is a de facto, framework-specific answer to exactly the "guaranteed termination" problem `ra-multi-agent.md`'s global invariant 2 requires every topology to solve some way.

## OpenAI Agents SDK

The OpenAI Agents SDK (see [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/)) defines agents, a handoff construct for transferring a conversation or task from one agent to another, guardrails that can validate input or output against a policy, and sessions for maintaining conversational state.

`ra-multi-agent.md`'s handoff contract explicitly names "the OpenAI Agents SDK's handoff construct" as one of `P16 Handoff`'s nearest equivalents. This is the most direct de facto implementation of `P16` in the landscape, and its existence is itself the argument (made in `P16`'s own justification, now in [`ra/primitives/`](../../ra/primitives/README.md)) that `P16 Handoff` and `P18 ArbitrationPolicy` have real, working implementations across the frameworks surveyed but no interoperable, cross-framework definition: a handoff built with the OpenAI Agents SDK's construct and a handoff built with LangGraph's `Command(goto=...)` are solving the same problem with no shared vocabulary or interchange format between them, and a workflow author who needs both (because their organization uses both) has no way to describe the handoff once and target either.
