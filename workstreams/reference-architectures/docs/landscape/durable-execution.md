# Durable Execution

Temporal, Dapr Workflow / Dapr Agents, Microsoft Durable Functions, Restate, and DBOS — code-first orchestration that survives process restarts by persisting progress and replaying or resuming from a durable log or database rather than from in-memory state alone. Part of the [landscape survey](README.md); see [`../references.md`](../references.md) for sourcing.

## Temporal

Temporal (see [Temporal documentation](https://docs.temporal.io/)) separates a **workflow** — the orchestration logic, which Temporal replays deterministically from its recorded event history to recover state after a crash or restart — from an **activity**, which is where non-deterministic or side-effecting work (a network call, a database write, a call to an LLM) actually happens. The workflow code itself is constrained to be deterministic because Temporal's fault-tolerance model depends on being able to replay the same workflow code against the same event history and get the same decisions out; anything that could produce a different result on replay (wall-clock reads, random numbers, network calls, and — sharply relevant here — a call to a non-deterministic LLM) has to be pushed into an activity, whose result is recorded in history and simply returned on replay rather than recomputed.

This produces a sharp, independently-derived architectural conclusion that matters directly to this RA: **Temporal's determinism requirement and an LLM's non-determinism are in direct tension, and that tension is exactly why the LLM call must live inside an activity and not inside workflow code.** Temporal did not design this for agents — it designed it for ordinary non-deterministic operations like network calls — but the constraint generalizes perfectly to an LLM call, which is simply the most extreme case of a non-deterministic operation Temporal's model has to push out of the replayable workflow. This is independent confirmation, from a durable-execution engine with no stake in agentic AI framing, of the same conclusion `ra-single-agent.md` reaches from the workflow-ownership argument: the agent lives inside a bounded step (an activity, or a child workflow invoking activities), not inside the deterministic control flow itself. Temporal's cross-mapping row in `ra-single-agent.md` reflects this: `P4 AgentStep` maps to "Activity or child workflow," and `P5 ToolCall` maps to "Activity invoked from within the AgentStep's Activity/child workflow" — the agent's tool calls are themselves further activities, nested one level deeper than the agent's own non-deterministic reasoning step.

**What Temporal gives for free:** durable state via event-history replay (`P12 StateCommit`'s mechanism), activity retry policies (`P9 ErrorBoundary`'s mechanism), durable timers (`P8 TimerDeadline`'s mechanism), a Signal for delivering external input to a running workflow (`P6 HumanCheckpoint`'s nearest equivalent), fan-out composed from child workflows and futures rather than a dedicated construct (`P7 FanOut/FanIn`'s nearest equivalent), and the saga pattern as a compensation idiom (`P11 Compensation`'s nearest equivalent, per `ra-single-agent.md`'s cross-mapping table). **What it does not give:** any native budget ceiling, and no first-class agent or tool-scope concept — an `AgentStep` and its `ToolCall`s are things a Temporal user builds *with* activities and child workflows, not things Temporal names.

## Dapr Workflow / Dapr Agents

Dapr (see [Dapr Workflow](https://docs.dapr.io/developing-applications/building-blocks/workflow/workflow-overview/); [Dapr Agents](https://dapr.github.io/dapr-agents/)) is built on an actor-based runtime, where Dapr Workflow's durable orchestration is itself implemented on top of Dapr's virtual-actor abstraction, and Dapr Agents extends that runtime toward agentic use cases specifically. Dapr's relevance to this WG is direct: per the [WG charter](../../../../charter/charter.md), the WG's chair, Yaron Schneider, is affiliated with Diagrid — making alignment between this RA's primitive set and Dapr Agents' model both a technical question (does Dapr Agents already have a de facto `Budget`, `Handoff`, or `ArbitrationPolicy`?) and a politically load-bearing one for the WG's own credibility (a WG chaired by a Dapr affiliate whose reference architecture diverges gratuitously from Dapr's own agentic runtime would be a visible inconsistency).

> **[verify]** The specific extent to which Dapr Agents already implements constructs equivalent to `P13 Budget`, `P16 Handoff`, `P17 SharedContext`, or `P18 ArbitrationPolicy` was not confirmed against Dapr's documentation this session and should be checked directly before this document asserts alignment or divergence as settled.

## Microsoft Durable Functions, Restate, DBOS

Microsoft Durable Functions, Restate, and DBOS are grouped here as further durable-execution systems in the same family as Temporal and Dapr Workflow: each provides a way to write orchestration logic that survives process restarts by persisting progress and replaying or resuming from a durable log or database rather than from in-memory state alone.

> **[verify]** This document does not have a verified source in its reference list for Microsoft Durable Functions, Restate, or DBOS specifically, and does not assert their specific API surface, terminology, or current feature set as fact. The general architectural pattern — durable orchestration logic separated from the effectful or non-deterministic work it calls out to, with progress persisted so execution can resume after a failure — is consistent with the public positioning of all three systems, but any specific claim about them (construct names, guarantees, current maturity) needs direct verification against their own documentation before this document, or any deliverable built on it, cites them as settled fact.

The relevant point for this RA does not depend on those specifics: every durable-execution system in this category exists to solve charter scope item **B — Long-Running and Stateful Agent Execution** for ordinary non-deterministic work (network calls, timers, human waits), and none of them was designed with an LLM call specifically in mind — which is exactly why Temporal's determinism-vs-non-determinism tension, argued in detail above, generalizes across this whole category rather than being specific to Temporal.
