# Gap Analysis

| Gap | Current state across the landscape | Why it matters | Candidate approach |
|---|---|---|---|
| Budget / cost ceilings | No reviewed standard or framework has a native cost ceiling; BPMN's `completionCondition` and Camunda's model-call limit are the closest partial mechanisms — see [`P13 Budget`'s own file](../ra/primitives/README.md) | Unbounded iteration is now a first-class operational and financial failure mode, independent of correctness | Declare the ceiling as part of the `AgentStep` contract's element 5, expressed today via BPMN `extensionElements` (per the Camunda precedent) or the equivalent extension mechanism in a code-first engine; a portable cross-runtime representation remains an open question in both RA files |
| Machine-checkable termination predicates | Expressible in every system surveyed (a `completionCondition`, a `Choice` state reading a validation task, a conditional edge reading a validation node) but named as a first-class construct in none — the same shape of finding as the budget gap above; see [`P19 EvaluationGate`'s own file](../ra/primitives/README.md) | An iterating `AgentStep` with nothing to test its output against exits only by exhaustion, not by success — the difference between a loop that converges and one that merely stops | `P19 EvaluationGate` declares the slot: the predicate itself, and how gate quality is evaluated, is the Accuracy & Reliability WG's domain, not this RA's — see [`reconciliation-log.md`](reconciliation-log.md) for the scope-change record |
| Confidence / uncertainty signalling in output contracts | No framework surveyed standardizes a confidence field; it is bespoke prompt engineering wherever it exists | Downstream `P3 Decision` primitives have nothing to route on without it; the RA's own anti-pattern list names "confidence-free output" as forcing either blanket auto-completion or blanket escalation | The `AgentStep` output contract's required confidence/uncertainty field (boundary contract element 3); how confidence is computed is explicitly the Accuracy & Reliability WG's interface, not this WG's |
| Termination classification interoperability | Every engine has its own terminal-state vocabulary (BPMN end events, A2A task lifecycle states — unverified specifics, Step Functions `Succeed`/`Fail`, Temporal completion status); none maps cleanly onto `P14`'s seven-value set | Cross-runtime portability (charter scope E) requires a shared termination vocabulary, or "completed" silently means different things in different systems | WG follow-up mapping table from `P14` to A2A's task lifecycle states, flagged as open work identically in both RA files |
| Effect classification as workflow-level, not server-level, concern | MCP provides tool annotations as hints and explicitly disclaims protocol-level enforcement of their trustworthiness | An untrusted or misconfigured server's self-description is not a security boundary; the RA's tool-scope contract exists because MCP said this would not be its job | A workflow-owned tool registry, populated independently of server-supplied annotations, feeding the `AgentStep` allowlist — see [`P4 AgentStep`'s own file](../ra/primitives/README.md) |
| Compensation for agent-caused effects | BPMN and Temporal have mature compensation/saga mechanisms; n8n and LangGraph, per `ra-single-agent.md`'s own table, have none | An agent's `reversible_write` that turns out wrong has no declared undo path — a real regression relative to pre-agentic durable execution, argued in [`P11 Compensation`'s own file](../ra/primitives/README.md) | Consider whether any `AgentStep` with a `reversible_write` tool in scope should carry a compensation obligation more strongly than the current SHOULD-level `P11` — a live question for the WG, not resolved here |
| Portable representation of the `AgentStep` boundary contract | Camunda's `zeebe:adHoc` element inside BPMN `extensionElements` shows the mechanism works for activation configuration; no reviewed system has attempted to express the full eight-element contract | Without a portable representation, the boundary contract exists only in this RA's prose, unavailable to any engine's validation or tooling | Two options, with trade-offs: (a) BPMN `extensionElements` — works today, no new notation, has the Camunda precedent, but is vendor-specific unless the WG agrees a shared schema; (b) a new BPMN element type — first-class, spec-validated notation, but requires an OMG-level standards process this WG does not control, with a multi-year adoption lag |
| Handoff audit correlation across organisational boundaries | A2A defines `contextId` and `taskId` fields for related purposes; no confirmed mapping to this RA's audit-continuity requirement exists yet (both RA files flag this identically) | T4's "audit gaps at organisational boundaries" failure mode is exactly a cross-org handoff crossing into a system this workflow's own audit log cannot see into | A WG-defined correlation-identifier convention, mapped to A2A's fields once their semantics are verified — explicit follow-up work named in both RA files |
| Memory and context as the least standardised layer | Both RA files explicitly decline to specify it; the prior proposal names it the least mature layer in its own open-questions section | `P16`'s context-transfer element and `P17`'s consistency model both depend on a memory layer with no shared vocabulary underneath either of them | Both RAs agree this is out of scope for this document; it is a dependency for whatever WG or workstream eventually takes it on, not a gap this RA should try to close itself |
| Workflow-definition portability across the systems surveyed | CNCF Serverless Workflow is the closest existing vendor-neutral DSL attempt; BPMN `extensionElements` is the closest existing extension mechanism; no system in the [landscape survey](landscape/README.md) can import another's workflow definition today | Charter scope item E is not satisfied merely by naming `P1`–`P19` — a shared vocabulary does not make a BPMN process importable into LangGraph, or vice versa | Treat the primitive set as the taxonomy layer ([`charter-mapping.md`](charter-mapping.md) argues this explicitly) and leave concrete interchange-format work as a distinct, later deliverable |

Read across the rows, a pattern emerges that is itself worth stating: the gaps cluster into two different kinds, and the WG should not treat them as equally tractable. Budget/cost ceilings, machine-checkable termination predicates, confidence signalling, termination-classification interoperability, and effect classification are all gaps in *contract content* — what a schema field should contain — and each already has a named place to live inside the `AgentStep`, `Handoff`, or (for the termination-predicate gap) `EvaluationGate` contracts this RA has already drafted; closing them is a matter of the WG agreeing on a field, not inventing a new mechanism. Portable representation of the boundary contract, handoff audit correlation across organisations, and workflow-definition portability are gaps in *interchange format* — how a contract, once agreed, actually travels between two different engines' native representations — and none of them has an obvious next step, because each depends on either an external standards body (OMG, for a new BPMN element) or an external protocol's own unresolved specifics (A2A's task lifecycle and correlation fields) that this WG does not control. Compensation and memory/context sit apart from both clusters: compensation is a gap this RA could plausibly close unilaterally by raising `P11`'s obligation level, while memory/context is a gap both RA files have deliberately declined to touch at all. A WG prioritizing its own next steps should expect the first cluster to be tractable within this WG's own drafting cycle and the second to require sustained cross-organisational coordination this WG cannot shortcut.
