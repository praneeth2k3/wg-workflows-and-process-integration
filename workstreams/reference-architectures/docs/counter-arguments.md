# Counter-Arguments and Criticisms

## "BPMN is the wrong substrate"

**The case:** graphical process notation is heavyweight relative to code-first development, developer adoption of BPMN outside regulated or already-BPM-invested enterprises is genuinely contested, and BPMN's token-based control flow was designed for processes whose paths are known in advance. That is the opposite of what an agent's reasoning produces.

**The response:** neither RA file requires BPMN. `ra-single-agent.md`'s own cross-mapping table gives n8n, AWS Step Functions, Temporal, and LangGraph equal billing alongside BPMN in every primitive row. None of those four is a graphical process notation, and two of them (Temporal, LangGraph) are entirely code-first. The primitive set is deliberately expressible in both families; BPMN's `extensionElements` is named as this RA's "most likely binding path," not its only one, precisely because Camunda's ad-hoc sub-process happens to be the most concrete existing evidence that a bounded `AgentStep` container is expressible in a standards body's own notation today, without requiring a new element type. The honest concession: BPMN's graphical modeling genuinely does carry real adoption friction for code-first teams, and this document does not have a citable statistic to quantify how much. Any specific adoption figure would need to be sourced and verified before being used in an external-facing argument.

## "Bounding the agent defeats the point"

**The case, and the best objection in this document:** if you constrain an agent's tool scope, budget, and termination this tightly, you have written a deterministic workflow with extra latency and extra cost, because the agent can only ever do what the bounds allow it to do. So why pay for an LLM call at all?

**The response** has to concede the case where the objection is fully right, because the RA itself already concedes it: `ra-single-agent.md`'s checklist states, as its first and most common correct answer, "can the task be fully enumerated at design time... If yes: pure deterministic workflow. No `AgentStep` needed... State this plainly: this is the most common correct answer, regardless of how 'AI-native' the initiative is framed." If a use case's every subtask is enumerable and its budget ceiling would, in practice, always resolve to a single iteration, the objection is not a counter-argument at all. It is this RA's own checklist working as designed, catching a case that should never have used an `AgentStep` in the first place.

Where the objection overreaches: bounding *authority and resources* is not the same claim as bounding *reasoning*. The eight-element boundary contract governs what an agent may touch (tool scope) and how much it may spend (budget) before it is halted or escalated. It says nothing about how the agent plans, reflects, or reasons inside those bounds. `ra-single-agent.md` states this explicitly and revisits it nowhere else in the document: "ReAct, plan-and-execute, reflection, and other internal reasoning loops are equally valid implementation choices *inside* the `AgentStep` boundary. This document is silent on which to use, deliberately." The genuinely open-ended cases this RA reserves for agents ("extraction from unstructured input," "planning over an open or unbounded set of subtasks") are open-ended precisely in the dimension the contract leaves unconstrained (how the agent reasons about an unenumerable input space) while being bounded in the dimension that matters for safety and cost (what it may do and how much it may spend while reasoning about it). The actual boundary the objection should be tested against, use case by use case, is whether the *subtask set* is genuinely unbounded: if it is, a tight authority/resource bound does not collapse the agent into a deterministic workflow; it makes an otherwise-unsafe open-ended reasoning task safe to run.

## "Standardising this early ossifies the wrong model"

**The case:** agentic patterns are moving quickly; a primitive set drafted in August 2026 risks encoding 2026's accidents (this year's dominant topology, this year's typical failure mode) as if they were durable architecture.

**The response** is sequencing plus a distinction between layers. Both RA files are explicitly draft v0.1, and `ra-single-agent.md` states outright that "whether it becomes a conformance profile with a test suite is an open question, not a commitment." This is descriptive-then-normative sequencing by design, not an oversight to be corrected later. More importantly, the vocabulary layer this document defends is more durable than the pattern layer it also documents: naming "the ceiling on agent resource consumption" `P13 Budget` does not commit the WG to any particular enforcement mechanism, and naming "the deterministic rule that resolves agent disagreement" `P18 ArbitrationPolicy` does not commit it to any particular arbitration algorithm. The pattern layer (for instance, `ra-multi-agent.md`'s recommendation that topology T1 "SHOULD be the default multi-agent topology") is far more exposed to being superseded by whatever the field converges on next; if it is, the underlying primitives named here do not become obsolete along with it, because they describe what any successor topology will still need to declare (a budget, an arbitration rule, a termination guarantee), not how today's topology satisfies that need.

## "Frameworks will converge on their own"

**The case:** LangGraph, CrewAI, AutoGen, and the OpenAI Agents SDK are all iterating quickly and borrowing ideas from each other already; standardization work is redundant with market convergence that will happen anyway.

**The response** is the cross-organisational case, where convergence cannot happen bilaterally by definition. `ra-multi-agent.md`'s topology T4 and its A2A binding exist for exactly the situation where two agents are "owned, operated, or authorised by different organisations" with no shared framework to converge within: if organisation A standardizes on LangGraph's `Command` semantics for handoff and organisation B standardizes on the OpenAI Agents SDK's handoff construct, "convergence" would require one framework's model to become authoritative for both, which is precisely the vendor lock-in charter scope item E exists to prevent. [`why-a-reference-architecture.md`](why-a-reference-architecture.md)'s own evidence cuts against the "convergence will happen on its own" reading in a second way: Camunda, n8n, LangGraph, and Temporal have already converged independently on the same bounded-container shape without agreeing on a name for it. That is evidence that a name is needed, not evidence that naming is superfluous, because independent convergence on a shape with no shared vocabulary is exactly the fragmentation problem that document opens with.

## "Too much ceremony for small use cases"

**The case, and a fair one:** the eight-element `AgentStep` contract and the seven-element `Handoff` contract are sized for production-grade, multi-stakeholder, auditable workflows. Applying either in full to a single-shot classification agent or a two-tool lookup script is disproportionate ceremony that will get skipped in practice, which is worse than not having the contract at all.

**The response** has to be honest rather than defensive: this is a real cost, and neither RA file has resolved it yet. `ra-single-agent.md`'s own open questions ask "whether to define a conformance profile and test suite for this RA, or leave it descriptive" without answering the question. A tiered or profile-based approach is the plausible shape of a resolution: a minimal profile requiring only the primitives that are cheap to satisfy even for a small use case (a declared trigger, a declared goal and output schema, a generous default budget ceiling) against a full profile requiring the complete eight- and seven-element contracts for anything touching an irreversible action, a cross-organisational boundary, or a regulated decision. Neither RA file commits to this today; it is named here as the most credible answer to a real objection, not as a settled position either document has taken.
