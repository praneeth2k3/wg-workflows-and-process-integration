# Why a Reference Architecture Is Needed Now

This is supporting analysis for [`../ra/ra-single-agent.md`](../ra/ra-single-agent.md) and [`../ra/ra-multi-agent.md`](../ra/ra-multi-agent.md). It does not introduce, redefine, or reinterpret any primitive; it argues why the primitives the two RA files already define look the way they do.

## The primitives already exist but the vocabulary does not

Every orchestrator surveyed in the landscape survey (see [`landscape/`](landscape/README.md)) has *some* retry construct, *some* parallel-execution construct, and *some* human-pause construct. BPMN has boundary events and user tasks; n8n has per-node retry settings and a `sendAndWait` operation; AWS Step Functions has `Retry`/`Catch` and `.waitForTaskToken`; Temporal has activity retry policies and signals; LangGraph has graph-level exception handling and `interrupt()`. None of these use the same name for the same idea, and — more importantly — **none of them has a resource-consumption ceiling construct at all**. `ra-single-agent.md`'s own cross-mapping table marks `P13 Budget` as "no native primitive" across all five reviewed systems.

This is exactly the problem the charter names in scope item **A — Agent Workflow Models and Semantics**: "industry adoption challenges across agent frameworks due to misalignment on key definitions and lack of knowledge in translating deterministic workflow models to non-deterministic models used by autonomous agents." A shared primitive vocabulary is the smallest useful artifact that addresses this directly, because it does not require any vendor to change their engine — it only requires agreeing what to call the thing each engine already half-has. It is also a direct instrument of scope item **E — Workflow Portability and Interoperability**: "enterprise environments will use multiple frameworks and need a standard way to communicate and share state across multiple technology stacks." A name is a precondition for portability; you cannot port a `Budget` across engines if only one of them has agreed to call it that.

## The failure mode is architectural, not model quality

Consider an agent given unbounded tool scope, no budget, no confidence signal on its output, and no termination predicate evaluated outside its own reasoning. That agent will fail in production — not eventually, but characteristically, and not because the underlying model is insufficiently capable. A better model does not add a budget where none was declared; a better model does not add a confidence field to an output schema that was never specified; a better model does not stop an unbounded tool-use loop that no external mechanism is watching. Each of these is a structural absence, not a competence gap, and improving the model that sits inside an unbounded structure improves how confidently it fails, not whether it fails.

This is the argument for a *reference architecture* — a specification of what has to exist around the model — rather than a better prompt or a better agent framework. A prompt is a request the model may ignore, misread, or reason around; `ra-single-agent.md` makes exactly this point about budget ("a budget stated in the prompt is a suggestion the model MAY ignore under its own reasoning; a budget enforced by the orchestrator is a hard stop the model cannot reason its way past") and about tool-scope enforcement ("the prompt is the guardrail" is listed as an anti-pattern). A framework improves the model's tools and ergonomics but does not, by itself, obligate a project team to declare a budget, a tool allowlist, or a termination condition — nothing stops a team from using LangGraph, or n8n, or Temporal, and still shipping an unbounded agent inside it.

The prior proposal cites analyst data supporting this architecture-misalignment thesis directly — see [`Workflows-and-Processes-Reference-Architecture-Proposal.md`](../../../Workflows-and-Processes-Reference-Architecture-Proposal.md), §2, on Gartner's projected agentic-project cancellation rate and its attribution to architecture misalignment, and on Forrester's *Adaptive Process Orchestration* category. This document does not restate those figures; the proposal is the citable source for them, and any external claim built on them should trace back to that section rather than to this one.

## Agentic execution is being retrofitted onto pre-agentic standards, right now, without a shared model

This is not a hypothetical future problem. Camunda has shipped an AI Agent Sub-process connector that puts agent reasoning inside a BPMN ad-hoc sub-process's job-worker implementation (see [Camunda — AI Agent Sub-process connector](https://docs.camunda.io/docs/components/connectors/out-of-the-box-connectors/agentic-ai-aiagent-subprocess); [Camunda — Ad-hoc sub-processes](https://docs.camunda.io/docs/components/modeler/bpmn/ad-hoc-subprocesses/)). n8n ships an AI Agent node with typed sub-node attachments for chat model, memory, and tools (see [n8n documentation](https://docs.n8n.io/)). LangGraph ships checkpointers, threads, and `interrupt()` as the durable-pause mechanism around agentic subgraphs (see [LangGraph documentation](https://langchain-ai.github.io/langgraph/)). Temporal's durability model is being reused, independently, as the substrate under agent runtimes that need to survive process restarts (see [Temporal documentation](https://docs.temporal.io/)).

Four independent engineering organizations, starting from four different notations and runtimes, converged on the same shape: a bounded container, a tool-attachment mechanism, and a durable-pause mechanism around a non-deterministic reasoning loop. That convergence, arrived at independently, is the strongest empirical evidence available that the shape this WG's primitive set names (`P4 AgentStep`, `P5 ToolCall`, `P6 HumanCheckpoint`, `P12 StateCommit`) is not an invention — it is a description of what four different production systems already needed to build. The window for naming that shape with a vendor-neutral vocabulary is open now precisely because none of these implementations has yet hardened into a de facto standard that the rest of the industry has to reverse-engineer around. It closes as each vendor's terminology entrenches in its own user base and documentation, and cross-framework translation becomes a matter of guesswork rather than a shared reference.
