# How This Maps to the WG Charter

| Charter scope item | RA sections and primitives addressing it | Gaps remaining |
|---|---|---|
| A: Agent Workflow Models and Semantics | The full `P1`–`P19` primitive vocabulary; the `AgentStep` boundary contract; the `T1`–`T6` topology catalog; `P16 Handoff`'s seven-element contract, which is the charter's own explicit example ("agent handoff semantics between agents and sub-agents") | Portable, cross-runtime representation of the primitives is still undefined (see the "Portable representation of the `AgentStep` boundary contract" row in [`gap-analysis.md`](gap-analysis.md)); no cross-framework conformance test exists |
| B: Long-Running and Stateful Agent Execution | `P12 StateCommit`, `P8 TimerDeadline`, `P9 ErrorBoundary`, `P15 AuditRecord`; `ra-multi-agent.md`'s reconstructable-audit invariant | The workflow-level-audit-vs-runtime-observability boundary is asserted but not yet tooled; no reference implementation exists to validate it against a real long-running deployment |
| C: Tool Invocation and External System Coordination | `P5 ToolCall`, the tool-scope effect classification, the MCP binding argued in [`P4 AgentStep`'s own file](../ra/primitives/README.md) | "Consistency patterns when agent workflows interact with external stateful systems" is named explicitly in the charter's own motivation for scope item C and is not addressed by either RA file. This is a real, unaddressed gap this document names plainly rather than papering over |
| D: Human-in-the-Loop Workflow Patterns | `P6 HumanCheckpoint`, `P10 Escalation`, the boundary contract's termination-conditions element, `ra-multi-agent.md`'s invariant placing `HumanCheckpoint` on irreversible or low-confidence outcomes | The regulatory threshold for when a `HumanCheckpoint` is legally mandatory, not merely architecturally advisable, is explicitly deferred to the Governance, Risk & Regulatory Alignment WG by both RA files' boundaries sections |
| E: Workflow Portability and Interoperability | `P16 Handoff`, the A2A binding, the cross-mapping tables spanning five-plus systems in `ra-single-agent.md` and `ra-multi-agent.md` | The least-served scope item as things stand: naming primitives is not the same as an interchange format (see the "Workflow-definition portability" row in [`gap-analysis.md`](gap-analysis.md)); CNCF Serverless Workflow is the nearest existing attempt and has no confirmed mapping to `P1`–`P19` today |
| F: Operational Patterns for Production Agent Workflows | The `T1`–`T6` topology catalog, both RA files' anti-pattern lists, both RA files' checklists | No reference implementation exists yet; the charter's own language about "best practices for operating and scaling different agentic workflows" overlaps with the separately targeted *Workflow Best Practices* deliverable rather than the *Workflow Reference Architecture* this document supports |

`P19 EvaluationGate` and the loop-tier model it depends on (see [`../ra/guidance/loop-tiers.md`](../ra/guidance/loop-tiers.md)) bear on two of the same scope items rather than opening a new one: scope item **A** (they are workflow semantics: a named slot for a termination predicate an iterating `AgentStep` reads) and scope item **F** (they describe an operational pattern: how a step's budget and its gate interact across nested loops at different cadences). The boundary that keeps `P19` inside this WG's remit rather than the Accuracy & Reliability WG's is exactly what keeps it narrow: this RA requires that the *slot* for a termination predicate exist and be evaluable by the orchestrator, and says nothing about what makes a good predicate, how gate quality is measured, or how evals are authored. That is the Accuracy & Reliability WG's domain. See [`reconciliation-log.md`](reconciliation-log.md) for the scope-change record.

This document feeds the **Workflow Reference Architecture** deliverable, targeted for 08.29.2026 per the [charter](../../../charter/charter.md)'s 3-Month Goals and Planned Deliverables sections (§4). That deliverable shares its target date exactly with the **Workflow Taxonomy** deliverable, also targeted 08.29.2026, and this document argues the two should not be developed as if they were independent. The primitive set *is*, functionally, a taxonomy contribution: it is a controlled vocabulary with defined terms, defined obligations (MUST/SHOULD), and defined relationships to prior art, which is what a taxonomy deliverable would otherwise have to produce from scratch. If the Workflow Taxonomy deliverable is drafted independently of the primitive set and lands on different names for the same concepts (a different name for what this RA calls `P13 Budget`, for instance), the WG will have shipped, on the same day, two deliverables that recreate exactly the vocabulary-fragmentation problem [`why-a-reference-architecture.md`](why-a-reference-architecture.md) argues a reference architecture exists to solve. The two deliverables sharing a target date is either a coincidence worth correcting through explicit coordination, or evidence the charter's authors already intended them to converge; either way, the practical recommendation is the same: align the Taxonomy deliverable's terms to the primitive set rather than developing the two documents in isolation from each other.
